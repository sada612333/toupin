## 项目整体架构

### 一、分层架构

项目采用三层架构设计：**基础层 → 核心层 → 应用层**

#### 1. 基础层
- **核心职能**：提供底层基础能力支撑
- **主要组件**：
  - 安卓原生 API（屏幕采集、音视频编解码、网络通信）
  - 网络基础（Socket、HTTP、WiFi 管理）
  - 权限管理（屏幕采集、网络、存储、热点）
  - 日志工具
  - Jetpack Compose 框架基础
  - WebRTC 核心依赖

#### 2. 核心层
核心层仅包含发送端模块与接收端模块，性能、连接等相关逻辑均融入对应模块。

**发送端模块**：
- 基于 Jetpack Compose 搭建 UI
- 屏幕内容采集
- 音视频编码
- 基于 WebRTC 实现局域网数据传输
- 性能管控
- 连接管理

**接收端模块**：
- 基于 Jetpack Compose 搭建 UI
- 数据接收
- 音视频解码
- 画面显示
- 性能管控
- 连接响应

**公共模块**：
- 工具类、通用组件、常量定义
- Jetpack Compose 通用组件
- WebRTC 公共配置

#### 3. 应用层
- **发送端**：基于 Jetpack Compose 的操作界面、用户交互、设置功能
- **接收端**：基于 Jetpack Compose 的显示界面、连接管理、状态反馈

### 二、模块间关联关系
```
发送端采集编码 → WebRTC 局域网传输 → 接收端解码显示
    ↓                ↓                ↓
  公共模块         公共模块         公共模块
    ↓                ↓                ↓
  基础层           基础层           基础层
```

### 三、当前架构痛点
- 代码重复：发送端与接收端存在大量重复代码
- 层级不清晰：部分代码跨层调用，职责划分模糊
- Jetpack Compose 组件复用性不足
- WebRTC 传输优化不到位

### 四、重构方向
- 提取公共模块，整合重复代码
- 明确各层职责，避免跨层调用
- 优化 Jetpack Compose 组件设计
- 完善 WebRTC 传输逻辑
- 注意依赖组件与 kitlon、gradle、安卓 gradle 插件的适配性

### 五、编码要求
- 单一功能点可验证、可测试，每个功能点独立设计测试逻辑
- 制定统一的日志结构规范，确保日志输出清晰、可追溯
